# Web Push Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Deliver optional background notifications with independent receiver preferences and useful monitoring availability events.

**Architecture:** Preserve durable notification records and email retries. Add encrypted receivers and a transactional push outbox, an independent monitoring-availability evaluator, authenticated management APIs and a push-only service worker. Extend existing React settings and notification history.

**Tech Stack:** TypeScript, React/Vite, Fastify, SQLite, Node 24, web-push, node:test.

**Spec:** `docs/superpowers/specs/2026-10-23-web-push-design.md`

## Global Constraints

- Single owner, existing authentication and origin protection, no new accounts or deployment.
- No private offline cache, extra Tuya polling or changes to energy accounting.
- Seven categories: threshold, anomaly, weekly, readings_lost, readings_restored, account_problem, account_restored.
- Defaults: every category selected except weekly; future categories off.
- Loss grace 15 minutes; recovery 5 minutes; operational TTL 1 hour; energy/weekly TTL 24 hours.
- All receiver controls, status, errors and push content support English and Polish.
- Preserve historical event IDs, immutable attempted email payloads and Resend idempotency keys.
- Explicit logout revokes the current receiver; password change revokes all; natural session expiry preserves opt-in.

## Review Focus

- Concurrent tabs, rotated subscriptions and lost local storage must not duplicate or silently reactivate recipients (Task 1/4).
- A failed receiver or slow provider must not starve collection, email or other receivers (Task 2/3).
- Tuya.ai device failures and idle integrations must not become account outages (Task 3).
- Recovery and configuration changes must not deliver misleading queued operational notices (Task 3).
- Logout, hostile endpoints and foreign notification-click destinations must preserve private-data boundaries (Task 1/4).

## File structure

- `shared/push.ts`: category constants, defaults and receiver/configuration/payload contracts.
- `server/pushSubscriptions.ts`: strict validation, encrypted persistence, preference cancellation, endpoint checks.
- `server/pushDelivery.ts`: outbox fanout, payload bounds, sender and retry loop.
- `server/notificationEvents.ts`: shared atomic event insertion and email preference semantics.
- `server/availability.ts`: persistent monitoring episodes, grouping and supersession.
- `server/pushRoutes.ts`: authenticated Fastify handlers, receiver session association and test delivery.
- `server/db.ts`, `config.ts`, `app.ts`, `notifications.ts`, `energy.ts`, `tuya-ai-integration.ts`: narrow integration points.
- `src/push.ts`, `src/PushSettings.tsx`, `src/locales/push.ts`: browser subscription lifecycle and settings controls.
- `public/sw.js`: push display and safe click navigation, without fetch handling.
- Existing shared types, settings/history components, translations, styles and docs updated in place.
